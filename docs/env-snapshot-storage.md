# Environment snapshot storage

`leerness env detect` refreshes `.leerness/environment.json`. The existing full-text `handoff --writeback` path refreshes it on first capture or when its existing comparison finds changed or missing tools. Both use the same canonical lock, strict captured UTF-8 source and checked publisher. Detection and comparison run inside that lock; a concurrent caller can time out under the existing lock policy if tool detection is slow.

Generated fields are `capturedAt`, `leernessVersion`, known fields in `os`, `hardware`, `locale`, `shell` and `node`, tool `version`/`path`, and dependency `command`/`usedBy`/`foundInPath`. Unknown top-level and nested metadata is retained. Tool membership and dependency rows reflect the new observation when a save occurs; notes on retained entries survive. If an absent tool or dependency has unknown fields, the save is refused with instructions to move those notes to top-level metadata first. This avoids silently deleting annotations or reporting absent tools as detected. Dependency identity is the pair of command and script name; ambiguous duplicate rows are refused.

Malformed UTF-8/JSON, non-object roots, incompatible known fields, unpaired Unicode and non-finite metadata numbers are refused without replacing the source. Older partial objects can be filled in. Source and output are bounded to 4 MiB. Valid Unicode, an existing UTF-8 signature and first LF/CRLF style are retained. JSON uses two-space serialization; this is semantic metadata preservation, not byte-exact preservation of arbitrary JSON whitespace, duplicate-key text, numeric spelling or precision beyond JavaScript's number representation. Historical corruption is not repaired.

An explicit failure returns a nonzero exit with the affected file, phase and available publication/recovery details. After a publication or lock-release failure, data or recovery artifacts may already exist; inspect the reported state before retrying. Earlier handoff output and other saved records are not rolled back. There is no whole-handoff transaction or exclusion of every external writer.

Default handoff, hooks, compact/quiet/JSON/pulse handoff, `--no-env-detect`, `LEERNESS_NO_ENV_DETECT=1` and explicit `env detect --no-write` retain their previous snapshot-write gates. An unchanged full handoff checks the captured source and leaves its bytes and modification time alone. Its existing comparison does not track every hardware or dependency change. Explicit detection still reports `persisted: true` and a failing exit when a missing script tool was detected after a successful save. The reported `snapshot` contains collected environment facts, while annotations remain in the saved file.

Tool discovery keeps its 5 s overall and 2 s per-attempt budget, FIFO tool order and error reporting. On Windows, up to 4 probes run at once: the calling thread plus up to 3 workers created for that one refresh, while `npm` and `git` always stay on the calling thread. Other platforms stay sequential whatever the setting. `LEERNESS_ENV_PROBE_CONCURRENCY=1` selects the sequential path on Windows; values above 4 are clamped. Concurrent Windows children can inherit each other's pipes and hold them for as long as they, or a process they leave behind, live. That can make a healthy tool time out or hide the tool at fault, so a timeout is not reported as it stands: it stops no lane, and after the lanes finish a sequential pass in tool order keeps the results, reports real failures, and runs a timed-out or unreached tool once more on its own inside the same budget. A tool that really hangs therefore costs up to two 2 s waits, and several hanging tools can use the whole 5 s where a sequential run stops at the first, each leaving behind whatever it started. When the 5 s budget runs out first, the reported tool can differ from a sequential run, and a run that a sequential refresh would finish can end as unknown; this takes a tool that leaves a long-lived process next to slow tools, most tools leaving one, or slow tools that hold each other up, for example on one free CPU or a shared lock. The existing snapshot is kept, and `LEERNESS_ENV_PROBE_CONCURRENCY=1` avoids it. Results are published in tool order. On a run that finishes, `where.exe` runs as in a sequential run, plus the lookups of each tool probed again (none for `git` and a bundled npm); a run that ends unknown can look up tools a sequential run would not have reached. Default reads start no probes or workers.

`npm run test:env-snapshot-text` exercises real CLI storage in temporary projects and isolated homes. Deterministic version probes avoid starting installed toolchains; tests cover concurrent CLI saves, malformed and stale inputs, annotation retention and partial-save reporting. Read-only observation quality, package/tool-output trust, other runtime writers, real-project rollout and deployment remain separate.
