# Stored-context reads and explicit handoff effects

Development candidate, updated 2026-10-30. This changes defaults; it is not a claim that an installed public package already behaves this way.

## Default reads

`leerness handoff [path]`, `handoff --json`, `handoff --compact`, `task list`, `state show`, `context current` and `hook session-start` read stored project data. They do not register a session, refresh environment inventory, run provider discovery or validation, write usage statistics, or automatically migrate a legacy workspace. No network is needed by these paths. Git location discovery and Windows console-encoding initialization are separate platform operations, not tool/provider inventories.

Handoff retains active rules, authoring/reporting policies, stored context and version-skew notices. A stored migration re-read notice remains visible in ordinary text output. Text, `--compact` and `--json` all report pending preview approvals, and an unreadable preview store stays distinct from an empty one. JSON keeps `files` and `memorySurface`, adds `nextTask`, and reports `inspection.status: "not_inspected"`; optional diagnostic fields are absent, not fabricated as healthy. Task-matched suggestions (related API skills and `apiSkills`, installed-skill suggestions, recalled lessons, brainstorm hits) follow the same rule: `handoff --inspect` shows them, and `health --json` and `session close --json` keep `apiSkills`. Compact output includes active rules rather than only their count. The existing owner-priority selector is shared with session-close. Ambiguous owner-priority markers fail with `invalid_owner_priorities`, rather than selecting an arbitrary task.

A default read reports what is stored about other sessions and adds nothing to it. Plain text, `--json`, `--compact` and `hook session-start` all report other sessions' records, a shared session address, an unreadable session store and pending agent reminders. Only `handoff --record`, `handoff --writeback`, `session close` and an MCP call with `sessionKey` write a session record. A session that has only read has no record, so it is invisible to others and its output says so (`not-recorded`, with `leerness handoff . --record`). Two sessions that only read cannot see each other: no other session listed does not mean no other session is running. `leerness sessions` lists the same records and what they cannot show. Plain text reads session records with the same link and file checks but leaves them out of the final revalidation, so another session recording at that moment cannot fail the read. `--json` and `--compact` keep the checked read and can stop with `Stored read sources changed; retry the read.`

## Loop state in a default read

A default read shows what `leerness loop` has recorded: `handoff`, `handoff --compact`, `hook session-start` and the MCP `leerness_handoff` print at most three stopped loops, `LOOP STOP L-0001 "<subject>" 3/3 rounds - owner decision required: leerness loop status L-0001` (with ` (<n> more after the cap)` after the round count when rounds were recorded after the STOP), then `and <n> more: leerness loop status` for the rest, and at most three open loops. `handoff --json` adds `loopGuard` (`schema: "leerness.loop-summary/v1"`, `state` `absent`, `present` or `unreadable`, with `open` and `stopped`, which list every loop; a loop with rounds after its cap also carries `overCap`). With no ledger nothing is printed and `loopGuard.state` is `absent`. A ledger that cannot be read (corrupt, over 262,144 bytes, a link or a non-regular entry at `.git/leerness/control` or below it, replaced while it was read) prints `LOOP LEDGER UNREADABLE (<code>)` and its path, and the read still exits 0. A `.git/leerness` that is itself a link or a file still fails the whole read with exit 1 (`layout_linked`, `layout_parent_invalid`), as it did before the merge. The same lines come from `handoff --inspect`, `--record` and `session close`. `handoff --pulse` and the multi-workspace forms (`--all-apps`, `--include`) do not print them.

What it costs: one checked read of one file below the Git common directory (`.leerness/loop-ledger.json` outside Git). The read takes the Git location from the snapshot it has made anyway (`lib/stored-read-snapshot.js` exposes it as `git`), so the loop lines start no process of their own, write nothing and create nothing, also when no ledger exists. The ledger is not one of the snapshot's revalidated sources: a peer that records a round while the read runs does not make it fail with `E_STORE_CHANGED`. A write is published by replacing the file, so a read that overlaps that moment can show the unreadable line for that one read. A STOP is a record the agent is told about, not a block: nothing here stops a command. If the project later enters Git, or is renamed inside a repository, the ledger is looked for in a different place, so its loops are not found and nothing is printed; the old file stays where it was and nothing says so.

## Explicit effects

| Command | Meaning |
| --- | --- |
| `leerness handoff . --record` | Request the existing ignored per-session freshness/presence records, without environment inspection. This is the command to use before an enforce-mode commit. |
| `leerness handoff . --inspect` | Request the retained legacy diagnostic path. This is not a read-only or cheap command: it can run tools, refresh caches and honor previously configured diagnostic recovery behavior. It does not certify overall health. |
| `leerness handoff . --writeback` | Retain legacy tracked writeback and diagnostic behavior. Existing write admission, locks and permissions still apply. |
| `leerness handoff . --record --no-record` | Read without a session receipt; `--no-record` wins. |

The one-line headline (drift level, secret findings, parent project), the six-step workflow guide and team schedule reminders print only on the diagnostic path (`--inspect`, `--writeback`, `--auto-recover`). `--inspect --compact` is rejected because diagnostic output is not a compact stored-context read. `--inspect` on other commands is rejected before side effects. `--auto-recover` remains an explicit legacy recovery request. A normal read is not an enforce receipt and does not bypass the existing hook or ownership checks. Existing generated hooks should be reinstalled to update their printed help; their actual freshness checks are unchanged. The Cursor session-start message distinguishes ordinary context reads from the explicit `--record` receipt request. Session-start selects the same owner-priority task as handoff; ambiguous priorities produce a warning with no arbitrary next task and do not block the editor hook.

The MCP `leerness_handoff` default likewise avoids usage and session writes. Supplying its existing `sessionKey` explicitly requests recording and retains its validation, suppression and ownership behavior. The advertised safe-write permission tier is unchanged: this work does not grant writes to read-only clients. MCP still uses the existing CLI adapter; moving to one direct library API remains later work.

## Consumer migration

See [the consumer transition matrix and public major-version decision](lean-readonly-compatibility.md). Repository checks and external installation acceptance are separate.

Code that needs diagnostics must request `--inspect` and tolerate partial or unavailable observations. Code that needs a freshness receipt must request `--record`, or provide the existing MCP `sessionKey`. Do not infer provider availability or test success from a context read.

The integrated doctor default is environment-only: `selftest.status = not_run`, `selftest.pass = 0`, `selftest.total = 0`, `selftest.ok = null`, `healthy = null`. Zero executed tests is not a passing suite. `LEERNESS_DOCTOR_SELFTEST=1 leerness doctor` remains explicit; its runner validation and failures are not weakened.

## Bounded explicit environment inspection

`leerness env detect [path]` and the environment-inventory portion of explicit handoff diagnostics share a 5,000 ms monotonic observation budget. Each attempt at a tool gets at most 2,000 ms including executable discovery, and on Windows a timed-out tool gets one more attempt inside the same overall budget; child stdout/stderr is bounded to 64 KiB. Probes run in the selected project directory, including npm and version-manager shims, not the caller's working directory. The existing shell-free launch boundary is retained. Only deadline-bearing observation calls request forced child termination; other process callers retain their previous options.

A missing executable (`ENOENT`) is absent, not an error. Timeout, excess output, unsupported shell wrappers and unsuccessful tool exits are **unknown**, not proof that a tool is missing. Explicit `env detect --json` returns nonzero with `E_ENV_PROBE_TIMEOUT` or `E_ENV_PROBE_INCOMPLETE` and `inspection: {status: "unknown", complete: false, ...}`. Raw tool stderr is not echoed. A failed collection leaves the prior environment snapshot and environment-tool cache unchanged, including user metadata. `--no-write` cannot create a snapshot on failure. An optional `handoff --inspect` emits an unknown-inventory notice and continues its other diagnostics; it does not certify a complete inventory.

The cache namespace is refreshed to discard inventories produced by the old ambiguous-error behavior. Existing project/PATH/version-file/executable fingerprints remain; npm's actual JavaScript entry point is also fingerprinted. Cache reuse is project-specific. No provider request, model execution or network service is added.

This is a child-observation budget, **not** a hard five-second end-to-end command deadline. Synchronous filesystem operations, scheduling, other explicit diagnostics and publication overhead are outside a hard real-time guarantee. Killing the direct child is not a general process-tree sandbox. Refresh does not persist a partial replacement snapshot. On Windows up to four probes run at once, a timeout stops no lane and a final sequential pass settles the result, as [environment snapshot storage](env-snapshot-storage.md) describes. Other platforms and `LEERNESS_ENV_PROBE_CONCURRENCY=1` stay sequential and stop on the first unknown result.

## Repeatable handoff measurement

`npm run benchmark:handoff` reports raw latency samples for 1,000 tasks and 20 recent log entries, with the owner-priority task selected. Thirty cold calls use distinct fixture paths and absent Leerness caches. Thirty warm calls use one fixture after a priming call. Every sample launches a fresh CLI, includes Node startup, and excludes fixture setup and assertions. The OS disk cache is not flushed; “cold” does not mean a cold operating system.

The result records fixture bytes, runtime/platform, exact source-file digests, nearest-rank p50/p95 and raw samples. `LEERNESS_BENCH_SOURCE` may bind it to the tested commit. The script checks output and fixture preservation but does not turn a performance target into a mandatory runtime gate. It measures the candidate, not a before/after improvement percentage. This fixture's output length does not implement the planned universal 8 KiB context limit.

## Verification and limits

`npm run test:lean-readonly` runs real CLI/MCP fixture calls, filesystem/process/network instrumentation, and project byte/name/mode/mtime comparisons. It covers non-ASCII paths, explicit recording, no-record precedence, owner priorities, active rules and stored migration notices. It uses no internal/no-migration/no-record bypass for the default-read cases. OFFLINE-unset contrast cases block and observe network APIs before transport and deny unexpected child commands; a deliberate blocked request verifies the instrumentation. Source-checkout cases use the actual project plan/tracker/handoff, not only simplified priority fixtures. Relevant lifecycle, MCP, diagnostic-cache and language probes retain their assertions but explicitly select the old optional effects.

LEAN-01A and this LEAN-01B follow-up are not completion of the entire design. It does not provide a bounded 8 KiB packet, a direct MCP service layer, a new state backend, task CAS, durable RunRecord finalization, a bounded parallel refresh engine or a performance SLA. Existing flat records can still be large. The 1,000-task benchmark is a separate developer command and does not run during ordinary handoff. No automatic installation update, state migration, npm/site/public release or deletion of existing APIs is performed.
