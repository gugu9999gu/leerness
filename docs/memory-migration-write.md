# Explicit memory migration

Local development CLI, first included in unreleased 1.36.194. Use this when
record-bearing decision or lesson Markdown cannot be safely regenerated by an
ordinary writer and canonical JSON is absent. The original bytes remain available
even when the existing parser cannot interpret every part of the document.

```sh
leerness memory-migration inspect decisions --path /path/to/project --json
leerness memory-migration prepare decisions --confirm --path /path/to/project --json
# Use the 32-character operationId returned by prepare:
leerness memory-migration apply decisions <operation-id> --confirm --path /path/to/project --json
leerness memory-migration rollback decisions <operation-id> --confirm --path /path/to/project --json
```

Replace `decisions` with `lessons` for lesson memory. Every command returns JSON;
exit 0 means its stated stage completed, exit 2 means rejection or partial failure.
`--confirm` is mandatory for all three write steps. Extra arguments, duplicate flags,
`--force` and `--dry-run` are rejected. Use `inspect` for read-only assessment.
The enforced policy tier is `project-write`; the existing canonical-file lock and
runtime write admission apply. Prepare can write lock/retention metadata but does
not change active memory. Existing `.harness` workspaces require explicit workspace
migration first. The MCP inspection tool stays read-only; it cannot apply migration.

## Stages and retained material

Prepare creates a new operation directory under
`.leerness/archive/memory-migrations/<operation-id>/` using exclusive creation.
It retains `source.md` byte for byte, including BOM and line endings, plus candidate
`canonical.json`, `projection.md`, a digest/identity manifest and `prepared.json`.
Files are flushed and reread before preparation succeeds. Existing artifacts are
never overwritten. Partial preparation may leave an incomplete directory: keep it
for inspection and prepare a new operation after resolving the cause.

Apply rederives and verifies the retained candidate, requires the original source
identity and absent canonical JSON, publishes canonical JSON, records its observed
identity in `canonical-created.json`, then replaces the Markdown projection. The
projection includes a relative link to the retained original. Ordinary subsequent
memory writes preserve that link. `applied.json` records the finished step.

Rollback verifies the retained bundle and matching live outputs, restores the raw
Markdown, and moves the attributed canonical object into an archive `withdraw-*`
directory before recording `rolled-back.json`. It does not delete the retained
source or bundle. Repeating a successful apply or rollback is a no-op on active
memory. A rolled-back operation cannot be reapplied: prepare a new operation.

## Failure and recovery

The response reports `stage`, `retentionVerified`, `retentionMayExist` and
`activeMutationStarted`. Failure after an active publication attempt is `partial`
even if the first write did not finish. A `recoveryReceipt`, when available, points
to before/live artifacts for manual inspection. Runtime admission failure may put
that receipt in a random directory in the user's temporary storage. Otherwise
returned retention paths are project-relative. Responses contain fixed metadata,
not memory entries or exception text. Archive files and recovery files contain the
original content and filesystem identity metadata, so handle them as project data.

If canonical publication was recorded but projection publication failed, retrying
apply can finish while the source remains the originally observed file. Rollback
can restore an attributed partial apply. Missing final receipts can be recreated
when all required state still matches. Corrupt/partial receipts, changed original
source, changed output bytes, and a canonical file without the matching creation
record are refused. In particular, a crash or error between canonical publication
and its ownership receipt requires manual recovery; identical canonical bytes
alone never authorize adoption or withdrawal. Preserve the archive and recovery
receipt and inspect both live files before manually resolving that case. Apply and
rollback mark their lock as kept for recovery: if the process is killed, the next
writer is not allowed to reclaim it. `inspect` is read-only and does not release
that lock. Stop all writers for this project, including writers on other computers,
and establish that the recorded owner has ended. A timeout, old timestamp or PID
alone is not proof. Preserve and compare the original owner record and lock
identity; if their provenance or the active paths are uncertain, stop.

For an explicitly approved recovery, verify the complete original bundle and
the current active files. If canonical JSON exists, require its matching
canonical ownership receipt. For an apply interrupted before canonical
publication, canonical JSON may be absent; the active Markdown must still have
the original prepared identity and bytes, and no canonical creation receipt
exists yet. Retain the entire confirmed-ended lock
directory by moving it to a unique, previously absent location on the same
filesystem. Check the absolute source and destination, refuse links or existing
destinations, and verify that the retained owner bytes and identity are unchanged.
This is a manual operator action, not automatic takeover or permission to discard
the lock. Keep the archive, lock record and recovery receipts as project data.
Then use the same original project and operation ID with the existing explicit
`apply` or `rollback` command. Missing required ownership evidence, changed live files or a
concurrent winner must stop recovery; do not choose an authority from identical
bytes, force adoption or overwrite later work. File observations and the manual
move are not an atomic transaction, so keep all writers stopped throughout.
Prepare does not touch active files and stays reclaimable.
A normal memory edit after apply will also prevent rollback if the expected
outputs differ. A kill can also leave a bundle or active file with a second name
(a publish links before it removes its temporary name); `inspect` and the migration
commands report codes only, so they do not name it. Any command that reads the file
through the memory input reader (`decision add` and `lesson save`, for example) refuses it with a
message that names the `.<name>.publish-<pid>-<24 hex>` file and says deleting that
name is safe.

## Limits

Input is limited to 1 MiB, combined candidate outputs to 4 MiB and manifest/receipt
reads to 16 KiB. Existing pure-assessment parsing budgets also apply. These limits
do not change ordinary writer item/count admission. Links, multi-link files,
unexpected directories, source changes and detected path retargeting are rejected.
Persisted identities are local observations, not signed attestations or portable
backup credentials. Moving the project or changing runtime/filesystem identity
reporting can require a new preparation.

`semanticCoverage` remains `unknown`: source retention prevents disposal of the
original, but does not prove that every sentence became a structured entry.
The process does not automatically roll back a multi-file failure. Checks and
publication/withdrawal are sequential, with no atomic snapshot or filesystem CAS
deletion guarantee. Cooperative CLI writers serialize through the existing lock;
noncooperative changes detected by checks cause refusal or a partial result.
File flushes do not prove directory durability, crash consistency or power-loss
recovery. Responses explicitly report `atomic: false`, `automaticRollback: false`
and `crashDurability: "unverified"`.
